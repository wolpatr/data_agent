# Open-source trading agents to adopt or borrow from — for a Python BTC/USDT spot paper-first bot (Bybit via Bybit EU)

**Research date:** 2026-11-09 · **Status:** findings file (research-only, no production code, no code changes) · **Method:** primary-source verification (official GitHub repos + GitHub's own repo API, official docs sites, PyPI pages, LICENSE files) over a live-fetch session; every fact below carries its dated source. Comparison table = verified facts only; unverified hunches are marked as such.

> **This file is findings only. It is research, not implementation guidance, and NOT investment advice.** Nothing here recommends buying, selling, or holding any asset, and a battle-tested bot framework is not evidence that any strategy is profitable.

---

## TL;DR — Recommendation

**Take inspiration + adopt infrastructure from freqtrade (adopt-and-configure), not build-from-scratch.** It is the only verified project that matches the v0.1 spec end-to-end out of the box: Python, hourly timeframes (1h among the documented timeframes), single-pair via pair whitelist, **Bybit spot officially supported** (CCXT-wired, `ccxt>=4.5.76` hard dependency), a **documented, unattended dry-run mode** (simulated wallet, no API keys needed, read-only exchange calls, restart-safe), full backtesting + hyperopt, an **explicit Bybit demo mode** (`exchange.demo_trading: true`) wired into the same config surface, active monthly releases (2026.8 → 2026.9 → 2026.10), and first-class docs. For the later "model improvement" phase it ships FreqAI (optional extras incl. reinforcement learning) behind the same strategy interface.

- **Closest to spec end-to-end: freqtrade — verified point-for-point** (see checklist in §7).
- **Best license for borrowing code:** Hummingbot (Apache-2.0) and Jesse (MIT) — permissive; but Hummingbot has **no Bybit spot candles feed** (fatal to an hourly-candle agent) and Jesse's **live/paper path is a license-keyed plugin**, not fully open.
- **Disqualified from adoption:** OctoBot (Bybit API currently impaired per its own README; 3.0 rework in beta), Superalgos (JavaScript/Node, wrong ecosystem), FinRL (self-described educational/research framework, live trading = "Basic Alpaca"), CryptoTrade (research prototype, stale 23 months, CC BY-NC-SA license).
- Academic code (CryptoTrade, FinRL) stays inspiration-only: CryptoTrade's reflective agent pattern (on-chain/news analysts + reflection) maps cleanly onto a future Evaluate module; FinRL pattern-maps to RL later. Neither touches venue plumbing.

## Verified facts, each with dated source

### 1. freqtrade — activity, license, packaging (criteria a, b, f)

- **Monthly release train, active development.** Latest release `2026.10` published **2026-10-30**; changelog includes "Add Orderbook websocket support", "Fully Decouple bot from RPC messaging for more reliable bot loop execution", "Dropped support for python 3.11", ccxt bumped through 4.5.90 (GitHub releases/latest, fetched 2026-11-09: https://api.github.com/repos/freqtrade/freqtrade/releases/latest). Release history `2026.9` (2026-09-29) and `2026.8` (2026-08-31) confirm the monthly cadence (https://api.github.com/repos/freqtrade/freqtrade/releases?per_page=5, fetched 2026-11-09).
- **Repo stats (GitHub's own API).** Language Python; license GPL-3.0; 56,685 stars; 11,719 forks; **pushed_at 2026-11-09T06:08Z**; open_issues_count 23; created 2017-05-17 (https://api.github.com/repos/freqtrade/freqtrade, fetched 2026-11-09).
- **License = GPL-3.0-only, in code.** `pyproject.toml` (develop branch, fetched 2026-11-09): `license = "GPL-3.0-only"`, `license-files = ["LICENSE"]` (https://raw.githubusercontent.com/freqtrade/freqtrade/develop/pyproject.toml). GitHub API concurs (GPL-3.0). Implication: **running freqtrade as a separate tool with our own config/strategy is fine**; copying/vendoring freqtrade source into our own codebase would make our codebase GPL-3.0-only too. For a private, single-user, local project this costs nothing in practice; it only bites if we ever distribute code derived from freqtrade's source.
- **Python ≥3.12; Windows supported; ccxt is a first-class dependency.** Same `pyproject.toml`: `requires-python = ">=3.12"`; classifiers 3.12/3.13/3.14; `"Operating System :: Microsoft :: Windows"`; dependencies include `ccxt>=4.5.76`, SQLAlchemy, fastapi; console script `freqtrade = "freqtrade.main:main"`. Optional extras: `freqai` (lightgbm, scikit-learn, tensorboard, xgboost), `freqai_rl` (gymnasium, sb3-contrib, stable-baselines3, torch), `hyperopt` (optuna, scikit-learn).

### 2. freqtrade — Bybit support incl. native demo mode (criterion c)

- **Bybit spot is a supported mode.** Docs "Quick overview of supported exchange features" table lists a **Bybit / spot** row (with `stoploss_on_exchange`: "❌ (not available)"; the futures Bybit row supports market+limit stoploss) — docs Exchange-specific Notes (fetched 2026-11-09: https://www.freqtrade.io/en/stable/exchanges/).
- **Native Bybit demo mode.** Same page, "Bybit Demo Mode": "Bybit has a demo mode - which can be activated by setting `exchange.demo_trading` to true in the configuration. Bybit uses live markets to simulate your trades (without market impact) - making it work very similar to freqtrade's dry-run mode. You'll need to use separate API keys for demo trading… **Demo mode is incompatible with dry-run.**" This is a one-config-flag path onto Bybit's demo service (the `api-demo.bybit.com` environment verified in `research/venue-ireland.md` §4 — the URL equivalence is an inference, mark for empirical confirmation; see gaps).
- **Bybit account caveats documented:** freqtrade assumes a bot-dedicated account/subaccount (same page, "Unified accounts").

### 3. freqtrade — dry-run mode built for unattended paper trading (criterion d)

- **Official docs "Using Dry-run mode":** "We recommend starting the bot in the Dry-run mode… the bot does not engage your money. It only runs a live simulation without creating trades on the exchange." Config: `"dry_run": true` + sqlite `db_url`. "**API Keys… are not required for the bot running in dry-run (trade simulation) mode**" (https://www.freqtrade.io/en/stable/configuration/, fetched 2026-11-09).
- **Simulation semantics are specified (deterministic enough for an unattended experiment):** wallets simulated from `dry_run_wallet` (default 1000); "Only Read-Only operations… are performed in dry-run mode"; "Market orders fill based on orderbook volume the moment the order is placed, with a maximum slippage of 5%"; "Limit orders fill once the price reaches the defined level - or time out based on unfilledtimeout settings"; "Open orders… are kept open after bot restarts" (same page, "Considerations for dry-run").
- **Hourly candles are in the box.** Configuration parameter table: `timeframe` — "The timeframe to use (e.g 1m, 5m, 15m, 30m, **1h** …)", set per strategy; docs even treat 1h-specific candle-timing edge cases (same page).

### 4. freqtrade — FreqAI: the "model improvement later" path (criterion e, later phases)

- **FreqAI is a maintained subsystem, not a bolt-on.** Official intro: "FreqAI is a software designed to automate a variety of tasks associated with training a predictive machine learning model to generate market forecasts given a set of input signals… FreqAI is, and always will be, a not-for-profit, open source project." RL support (stable-baselines3, gymnasium, torch) matches the future "model improvement" ambition of the project frame.

## The fork, framed honestly: (A) adopt-and-configure vs (B) build our own agent

**(A) Adopt freqtrade, configure it, write our own strategy file.**
- *Evidence for:* every v0.1 criterion verified above passes or passes-with-a-caveat; the hard, unglamorous infra — order-simulation semantics, restart persistence (sqlite), exchange error handling via a maintained CCXT pin, candle data download, backtesting/hyperopt, API-server/freqUI monitoring (in docs nav), monthly security-patched releases — exists and is exercised by ~57k stars' worth of users. The 2026.10 release notes headline exactly the resilience work ("Fully Decouple bot from RPC messaging for more reliable bot loop execution") that our unattended agent would otherwise have to hand-build.
- *Evidence against / costs:* GPL-3.0 — irrelevant for private use, but any future redistribution of copied source carries the copyleft obligation; the strategy lives **inside** their framework (callbacks, pairlists, trade objects) — loop-level autonomy beyond strategy callbacks means customizing their codebase, not writing ours; we inherit their abstractions (config schema, db schema) and their monthly breaking-changes rhythm (e.g., dropped Python 3.11 in 2026.10); Bybit-spot `stoploss_on_exchange` unavailable (our stop-loss lives in dry-run simulation only); Bybit demo mode and dry-run are mutually exclusive — we must pick per phase.
- *Net:* for "infra before model", this is weeks saved vs reinventing paper-order simulation. The known failure modes (exchange API drift, funding/fee edge cases visible in their changelogs) are exactly the ones a solo builder discovers slowly.

**(B) Build our own Python agent, borrowing architecture patterns.**
- *Evidence for:* full ownership of the agent loop — our Observe/Decide/Evaluate modules stay first-class, not wedged into callbacks; permissive-code options exist for reference patterns (Hummingbot's Apache-2.0 connector/paper-trade structure, Jesse's MIT backtest engine, CryptoTrade's reflective-decision shape for the later model phase, FinRL gym-env abstractions); CCXT itself (our already-chosen library) covers the venue API.
- *Evidence against / costs:* we must re-derive, alone, everything verified above that freqtrade documents as done: simulated-fill semantics that survive restarts (their spec: orderbook-based fills ≤5% slippage, limit-fill/timeout rules, open-order persistence), Bybit error-code handling, candle-store management, backtesting with lookahead protection. Each is a small correctness trap; paper-trading results are only meaningful if simulation rules are stable and honest. Expected cost: multiple weeks of unglamorous infra before any strategy question can even be asked.
- *Net:* choose (B) only if the project's center of gravity is the agent architecture itself (autonomous loop, custom tooling) rather than fastest time-to-unattended-paper-run. The project frame ("infra before model", simple research-cited trigger for v0.1) points the other way.

**Honest middle path (recommended shape):** adopt freqtrade for v0.1 infra; implement the research-cited trigger as a plain freqtrade strategy; keep our own agent design doc alive using CryptoTrade's reflection loop + FinRL env vocabulary as the long-term map; when the model phase begins, evaluate FreqAI (same process, same infra) vs migrating our own layer on top. Nothing in (A) prevents later (B) — strategies and data (sqlite/freqtrade JSON stores) are extractable.

## Recommendation recap (mapping to criteria)

1. **(a) Activity:** freqtrade monthly releases through 2026.10 — strongest, most predictable cadence of all candidates (all candidates except CryptoTrade and Superalgos were active within the last 30 days; only freqtrade ships a monthly train with a public changelog).
2. **(b) License:** GPL-3.0-only = zero-cost for private local use; document that any code donation from freqtrade into our repo binds those files to GPL-3.0. If we ever want to vendor connector-quality Python, Hummingbot (Apache-2.0) is the permissive donor of record.
3. **(c) Bybit spot:** verified supported in-box (CCXT wiring, spot row in the official features table; config-time Bybit demo mode).
4. **(d) Paper-first unattended:** dry-run is an explicitly recommended, documented mode with no API keys, simulated wallet, and restart persistence; alternative = `exchange.demo_trading: true` for Bybit-side demo (choose per phase; mutually exclusive).
5. **(e→g) Backtesting/docs:** native backtesting/hyperopt + FreqAI adaptive-retraining backtests; Python ≥3.12 (Windows classifiers present); large stable docs site — the best solo-builder surface verified here.

## Gaps and uncertainties to record on the map

1. **Bybit EU (bybit.eu) endpoint compatibility with freqtrade's `bybit` class not verified.** Freqtrade docs and CCXT default to globally-hosted bybit.com endpoints; whether Bybit EU accounts require distinct base URLs (and whether freqtrade's documented `exchange.ccxt_config` override suffices) must be empirically confirmed after account setup — same verification checklist as `research/venue-ireland.md`.
2. **`exchange.demo_trading: true` ↔ `api-demo.bybit.com` linkage is inferred, not source-verified** (freqtrade docs do not name the demo hostname; the URL equivalence comes from the Bybit v5 docs verified in venue-ireland.md). Run a one-shot connectivity test before relying on it. Note also Bybit demo orders are retained 7 days per Bybit's own docs (venue-ireland.md §4) — relevant for long unattended paper runs.
3. **freqtrade dry-run fill realism has known bounds** (orderbook-based fills, ≤5% slippage cap, stoploss assumed filled) — by design; treat dry-run P&L as a wiring-and-lifecycle test, not a profitability estimate. Quantifying dry-run-vs-demo-vs-live divergence is unscheduled follow-up work.
4. **Bybit demo mode × spot × freqtrade combination** is documented by freqtrade generally but the docs' demo section sits next to futures-specific notes; the exact spot-demo edge cases (e.g., funding-fee absence on spot demo) were not empirically tested this session.
5. **GPL-3.0 strategy-file interpretation** (whether a strategy we author against freqtrade counts as a derived work for distribution purposes) is a licensing judgment call not resolved by freqtrade's docs this session; moot while the project stays private.
6. **Jesse's license terms for the live/paper plugin** (free tier? pricing? redistribution rights) were not investigated — the gating itself is verified from official docs, its economics are not.
7. **OctoBot's Bybit "will soon be available again"** status is a point-in-time README note (2026-11-09); re-check if the adopt decision ever flips toward OctoBot, and expect 3.0-beta instability until a stable release.
8. **CryptoTrade / FinRL results not independently re-run**; CryptoTrade's own example output reports "sharpe ratio: inf" — prototype-grade benchmark hygiene. Their value here is architectural pattern, not numbers.
9. **arXiv pages for FinRL (2111.09395) and CryptoTrade (2407.09546) were not re-fetched this session** (both referenced from RESOURCES.md; the repos themselves were verified directly). EMNLP 2024 status of CryptoTrade is corroborated by the official repo description + README citation block (aclanthology.org/2024.emnlp-main.63).
10. **Hummingbot's V2 backtesting capability for candle-driven hourly spot strategies** was verified only at the level of repo topics and release notes — no hands-on assessment; its missing Bybit spot candles feed is the binding constraint regardless.
