## 1. Multi-pair mechanics in freqtrade

### 1.1 Pairlists: Static vs Volume — reproducibility in backtests

- `StaticPairList` (the default "if not configured differently") uses `exchange.pair_whitelist` / `pair_blacklist`; supports regex (`.*/USDT`). **Verified** — https://www.freqtrade.io/en/stable/plugins/#static-pair-list
- `VolumePairList` selects `number_assets` top pairs by `sort_key` (only `quoteVolume`), refreshing on `refresh_period` (default 1800 s) when in the leading position. **Verified** — https://www.freqtrade.io/en/stable/plugins/#volume-pair-list
- **"`VolumePairList` does not support backtesting mode."** Same statement for `PercentChangePairList`, `DelistFilter`, `FullTradesFilter`, `PerformanceFilter`. **Verified** — plugins page (respective sections; e.g. https://www.freqtrade.io/en/stable/plugins/#volume-pair-list).
  - Consequence (factual, not a decision): a dynamic volume-driven pairlist is not usable in `freqtrade backtesting`; reproducible backtests require a **static** whitelist (or a constant-composition dynamic list).
- FreqAI docs add a hard constraint: "**FreqAI cannot be combined with dynamic `VolumePairlists` (or any pairlist filter that adds and removes pairs dynamically)** […] FreqAI does work with the `ShufflePairlist` or a `VolumePairlist` which keeps the total pairlist constant (but reorders the pairs according to volume)." **Verified** — https://www.freqtrade.io/en/stable/freqai/#common-pitfalls
- `ShuffleFilter` accepts a `seed`; "You may set the `seed` value for this Pairlist to obtain reproducible results" (applied automatically in backtesting modes only). **Verified** — https://www.freqtrade.io/en/stable/plugins/#shufflefilter
- "Testing pairlists … Best use freqUI in webserver mode or the `test-pairlist` utility sub-command". **Verified** — plugins page, testing-pairlists note.

### 1.2 `max_open_trades` semantics with multiple pairs

- "Number of open trades your bot is allowed to have. **Only one open trade per pair is possible, so the length of your pairlist is another limitation** that can apply. If -1 then it is ignored (i.e. potentially unlimited open trades, limited by the pairlist)." **Verified** — https://www.freqtrade.io/en/stable/configuration/ (parameters table).
  - So with N whitelisted pairs and `max_open_trades: k`: at most `k` concurrent trades, and never more than one trade per pair; the binding constraint is `min(k, N)` at any moment.
- Factual scaling note for dry/live signal latency: "In dry and live, this may be delayed due to **all pair dataframes needing to be analysed first, then trade processing for each of those pairs happens**. This means that in dry/live you need to be mindful of having as low a computation delay as possible, usually by running a low number of pairs." **Verified** — https://www.freqtrade.io/en/stable/strategy-customization/#trade-order-assumptions (Signals vs Trades / Trade order assumptions section).

### 1.3 Capital: fixed stake vs unlimited

- **Fixed (static) stake:** "The `stake_amount` configuration statically configures the amount of stake-currency your bot will use for each trade. This setting works in combination with `max_open_trades`. **The maximum capital engaged in trades is `stake_amount * max_open_trades`.**" Example given: `max_open_trades=3`, `stake_amount=0.05` BTC → max 0.15 BTC engaged. **Verified** — https://www.freqtrade.io/en/stable/configuration/#static-stake-amount
  - Current v0.1 config: 250 × 1 = 250 USDT engaged cap. With 3–6 pairs unchanged config (`stake_amount: 250`), the engaged cap becomes 750–1500 USDT against a 1000 USDT dry-run wallet.
- **`tradable_balance_ratio`** (default 0.99): "the complete amount - 1% is at its disposal … when using dynamic stake amount, it will split the complete balance into `max_open_trades` buckets per trade." It applies to *current* balance (free + tied), so the untouched amount shrinks if the wallet shrinks. **Verified** — https://www.freqtrade.io/en/stable/configuration/#tradable-balance
- **Unlimited (dynamic) stake:** set `stake_amount: "unlimited"`; trade amount = `currency_balance / (max_open_trades - current_open_trades)`; docs recommend `tradable_balance_ratio: 0.99` alongside; "This configuration will allow increasing/decreasing stakes depending on the performance of the bot (lower stake if the bot is losing, higher stakes … profit compounding)." **Verified** — https://www.freqtrade.io/en/stable/configuration/#dynamic-stake-amount
- **`available_capital`:** starting capital per bot when running multiple bots on one account; "The bot will then split this starting balance equally into `max_open_trades` buckets." Incompatible with `tradable_balance_ratio`. **Verified** — https://www.freqtrade.io/en/stable/configuration/#assign-available-capital
- **`amend_last_stake_amount`** (default false) + `last_stake_amount_min_ratio` (default 0.5): reduces the last stake so the final slot can still fill (example: balance 1000, `stake_amount` 400, `max_open_trades` 3 → trades of 400/400/200); only applies with static stake. **Verified** — https://www.freqtrade.io/en/stable/configuration/#amend-last-stake-amount
- Fees matter for sizing: `fee` (config, "Fee used during backtesting / dry-runs … Fee is applied twice for each trade, once when buying, once when selling"), and the bot reserves `amount_reserve_percent` (default 0.05) + stoploss when computing minimum stake. **Verified** — configuration parameters table + minimum-trade-stake section.

### 1.4 Candle access, `--timeframe`, informative pairs

- `timeframe` is a Strategy-Override parameter (config may specify; CLI accepts `--timeframe`, e.g. `freqtrade backtesting --timerange 20190101-20190201 --timeframe 5m`). **Verified** — configuration table; https://www.freqtrade.io/en/stable/strategy-customization/#strategy-startup-period
- **Informative pairs:** strategies can request data for non-tradeable pairs via `informative_pairs()` returning `("pair", "timeframe")` tuples; "OHLCV data for these pairs will be downloaded as part of the regular whitelist refresh process and is available via `DataProvider` … These pairs will **not** be traded unless they are also specified in the pair whitelist." Docs warning: "As these pairs will be refreshed as part of the regular whitelist refresh, **it's best to keep this list short**." **Verified** — https://www.freqtrade.io/en/stable/strategy-customization/#informative-pairs
- Multi-timeframe access helpers: `@informative` decorator (with caching; "The informative function will only be called when a new informative candle is available (live/dry only)") and `merge_informative_pair()` ("Merge the dataframe without lookahead bias… Forward-fill (optional)"). **Verified** — same page, decorator and merge sections.
- Data-scale caps (live/dry): `startup_candle_count` should be below `ohlcv_candle_limit * 5` (500 × 5 for most exchanges); multi-candle fetches warn ("Using 3 calls to get OHLCV…") and are "capped to 5 total calls". **Verified** — strategy-customization startup-period section.
- `FullTradesFilter` (no backtest support): shrinks the whitelist to in-trade pairs when slots are full — a documentation-documented CPU optimization "since no new trade can be opened" — recommended at position 2 under a primary pairlist. **Verified** — plugins page #fulltradesfilter.

## 2. Rail redesign facts under multi-pair

All protections live **in the strategy** (config-level `"protections"` removed 2024.10). **Cross-ref** — `research/freqtrade-risk-rails.md` §3 (develop-source verified); also **Verified** this run on the stable plugins page: "Protections will protect your strategy from unexpected events and market conditions by temporarily stop trading for **either one pair, or for all pairs**. All protection end times are rounded up to the next candle." Backtesting/hyperopt support requires `--enable-protections`. **Verified** — https://www.freqtrade.io/en/stable/plugins/#protections

### 2.1 CooldownPeriod — pair-level only

- Docs list description: "**CooldownPeriod** — Don't enter a trade right after selling a trade." There is no `only_per_pair` knob on this protection in docs examples; the source treats it as pair-scoped (locks the pair of the just-closed trade from its `close_date + stop_duration`; ignores `lookback_period` because it "only looks at the latest trade"). **Verified** (docs description) https://www.freqtrade.io/en/stable/plugins/#cooldown-period + **Cross-ref** (`cooldown_period.py` semantics verified in the prior rails file §3).
- Under 3–6 pairs (factual consequence): each pair independently gets its post-exit cooldown; exits on one pair do not delay entries on others. With v0.1's single pair the pair-level scoping was invisible (per-pair = global when N=1).

### 2.2 StoplossGuard — `only_per_pair: False` is a GLOBAL stop across all pairs

- Docs, exact wording: "`StoplossGuard` selects all trades within `lookback_period` … If `trade_limit` or more trades resulted in stoploss, trading will stop for `stop_duration` … **This applies across all pairs, unless `only_per_pair` is set to true, which will then only look at one pair at a time.**" **Verified** — https://www.freqtrade.io/en/stable/plugins/#stoploss-guard
- Additional verified facts on the same section: it considers trades exiting as `"stop_loss"`, `"stoploss_on_exchange"`, `"trailing_stop_loss"` **if profit was negative** (default `required_profit: 0.0`); "For futures bots, setting `only_per_side` will make the bot only consider one side, and will then only lock this one side". **Verified** — same page.
- Cross-ref details (develop source, prior rails file §3): `only_per_pair: True` **disables the global stop** (stored as `_disable_global_stop`); with `only_per_pair: False` a trigger creates an all-pairs (`pair = "*"`) lock; locks block **entries only** and are DB-persisted in dry-run.
- Under 3–6 pairs (factual consequences, no decision):
  - The global counter aggregates losing stoplosses **from all pairs** within the 24-candle lookback. v0.1's `trade_limit: 2` is currently calibrated to a single-pair trade flow; with N simultaneously-trading pairs, the same threshold is reached proportionally faster (each pair contributes its own stoplosses to one bucket).
  - "One bad pair globally locks all entries" is a literal doc/source consequence: stopouts on pair A set an all-pairs lock (`pair = "*"`), stopping entries on pairs B…F for `stop_duration_candles` after the last counted trade.
  - The knob that reverses global scope is `only_per_pair: True` (per-pair evaluation; global stop disabled). `trade_limit` semantics = "Number of trades required at minimum" (common-protections table, **Verified** plugins page). Re-deciding these values is out of scope for this document.

### 2.3 MaxDrawdown — global-only, realized drawdown

- Docs: "The `MaxDrawdown` protection evaluates trades that closed within the current `lookback_period` (or `lookback_period_candles`). It supports 2 calculation modes: `calculation_mode: "ratios"` (default): Legacy approximation based on cumulative profit ratios. `calculation_mode: "equity"`: Standard peak-to-trough drawdown on the account equity curve, using starting balance and cumulative absolute profit. … For new setups, `calculation_mode: "equity"` is recommended." "If the observed drawdown exceeds `max_allowed_drawdown`, trading will stop for `stop_duration` after the last trade." **Verified** — https://www.freqtrade.io/en/stable/plugins/#maxdrawdown
- Scope: MaxDrawdown is **global-only** — there is no `only_per_pair` knob for it in docs or source (`has_local_stop = False`). **Cross-ref** — prior rails file §3 (develop source `max_drawdown_protection.py` verified). It uses closed trades only, i.e. *realized* drawdown; open positions' floating losses are invisible to it. **Cross-ref** — prior rails file §7.
- Under 3–6 pairs (factual consequences): the single global drawdown metric now absorbs realized losses from **every** pair; with `trade_limit: 5` over 168 candles and many concurrent closed trades, the threshold and lookback fill/refresh differently than in the 1-trade-slot regime. Its all-pairs lock (`*`) again blocks new entries everywhere during the stop window. The equity-mode baseline is "starting balance + cumulative absolute profit before the window" (`wallets.get_starting_balance()` + closed `close_profit_abs`). **Cross-ref** — prior rails file §3/§7.

### 2.4 The per-pair analog exists

- `LowProfitPairs` is the documented pair-level protection ("Lock pairs with low profits"): sum of `close_profit` over ≥ `trade_limit` closed trades of a pair within lookback < `required_profit` → locks **that pair** only. **Verified** (docs) — https://www.freqtrade.io/en/stable/plugins/#low-profit-pairs; source semantics **Cross-ref** — prior rails file §3. Listed here as fact (the pair-scoped counterpart of MaxDrawdown/StoplossGuard), not as a recommendation.

### 2.5 Common consequences for all protections under multi-pair

- Protections **block entries only** (exit paths check no locks); with multiple pairs, a lock can coexist with open trades on unlocked pairs continuing to be managed (exits/ROI/stoploss unaffected). **Cross-ref** — prior rails file §4 (`freqtradebot.py` verified).
- Lock end times round up to the next candle; every closed trade already gets a 1-candle "Auto lock" pair lock before protections are evaluated. **Cross-ref** — prior rails file §3.
- Docs example values in the current stable page use `StoplossGuard` with `trade_limit: 4, lookback_period_candles: 24, stop_duration_candles: 4` and `"only_per_pair": False` — i.e. the docs' own global-scope example; trade_limit/lookback "will need to be tuned for your strategy". **Verified** — Stoploss Guard section.

## 3. FreqAI classifier architecture (stable docs)

### 3.1 How FreqAI plugs into a strategy

- Minimum config (docs' "must at minimum include"): `"freqai": { "enabled": true, "purge_old_models": ..., "train_period_days": ..., "backtest_period_days": ..., "identifier": "unique-id", "feature_parameters": { "include_timeframes": [...], "include_corr_pairlist": [...], "label_period_candles": ..., "include_shifted_candles": ..., "indicator_periods_candles": [...] }, "data_split_parameters": { "test_size": ... } }`. `identifier` is "a unique ID that you choose to describe one of your runs"; change it (or delete `user_data/models/unique-id`) whenever features/model change — same `identifier` = model reuse/crash resilience. **Verified** — https://www.freqtrade.io/en/stable/freqai-configuration/#setting-up-the-configuration-file
- Strategy integration (exact functions, docs code):
  - `populate_indicators()` calls `dataframe = self.freqai.start(dataframe, metadata, self)` — "The `self.freqai.start()` function cannot be called outside the `populate_indicators()`." **Verified** — freqai-configuration #building-a-freqai-strategy
  - `feature_engineering_expand_all()` / `feature_engineering_expand_basic()` / `feature_engineering_standard()` build features (all prepended `%`); **"Features must be defined in `feature_engineering_*()`. Defining FreqAI features in `populate_indicators()` will cause the algorithm to fail in live/dry mode."** **Verified** — same page.
  - `set_freqai_targets()` defines labels (prepended `&`). **Verified** — same page.
  - `startup_candle_count` set as usual (largest indicator period; docs suggest multiplying by 2 for TA-Lib safety). **Verified** — freqai-configuration #setting-the-startup_candle_count
- Returned dataframe keys: predictions come back under the **same** label keys (`&-s_close` etc.) for use in `populate_entry/exit_trend()`; `&*_std/mean` label statistics; `do_predict` ∈ [−2, 2] trustworthiness flag (== 2 means "the model has expired due to exceeding `expired_hours`"); `DI_values` dissimilarity index. **Verified** — freqai-configuration #important-dataframe-key-patterns

**Verified** — https://api.github.com/repos/freqtrade/freqtrade/contents/freqtrade/freqai/prediction_models?ref=stable ; the sklearn wrapper verified by reading https://raw.githubusercontent.com/freqtrade/freqtrade/stable/freqtrade/freqai/prediction_models/SKLearnRandomForestClassifier.py

Marked: **Verified** for what exists; the "how to add others" path is doc-verified.
- PyTorch classifiers must declare `self.freqai.class_names` in `set_freqai_targets`. **Verified** — freqai-configuration PyTorch section.

### 3.3 Target-label design for classification

- "If you are using a classifier, you need to specify a target that has **discrete values** … the classes need to be set using **strings**. For example, if you want to predict if the price 100 candles into the future goes up or down you would set `df['&s-up_or_down'] = np.where(df['close'].shift(-100) > df['close'], 'up', 'down')`." **Verified** — freqai-configuration #classifiers
- Multi-class into one column: "If you want to predict multiple targets you must specify all labels in the same label column" — example adds a `'same'` class via a second `np.where` on equality. **Verified** — same section. (I.e. long/exit/hold-style labels are expressed as string classes in a single `&…` column; "multiple targets" for classifiers = multi-class in one column, whereas *multi-target* adapters cover several label columns for regressors/classifiers via the `MultiTarget` variants.)
- `label_period_candles` = "Number of candles into the future that the labels are created for" (feature_parameters table; "not necessarily required, you can create custom labels"). **Verified** — https://www.freqtrade.io/en/stable/freqai-parameter-table/
- Helpers for label building: `buffer_train_data_candles` (trim argrelextrema edges after target computation), `shuffle_after_split` (default False), `reverse_train_test_order` (default False; docs warn "understand the unorthodox nature"). **Verified** — parameter table.

### 3.4 Backtesting support + cost modeling

- Backtesting command: `freqtrade backtesting --strategy … --freqaimodel … --timerange …`. "FreqAI will train a new model **for each pair, for each backtesting window** within the expanded `--timerange`." **Verified** — https://www.freqtrade.io/en/stable/freqai-running/#backtesting
- **Sliding-window mechanics:** train window = `train_period_days`; prediction window = `backtest_period_days` (float allowed → sub-daily retraining). "After the training of the model, FreqAI will backtest the subsequent 7 days. The 'sliding window' then moves one week forward (emulating FreqAI retraining once per week in live mode) and the new model uses the previous 30 days (**including the 7 days used for backtesting by the previous model**) to train. This is repeated until the end of `--timerange`." Number of models = timerange ÷ `backtest_period_days` **per pair**; fractional windows multiply training count ("10 days ÷ 0.1 → 100 models **per pair**"). **Verified** — freqai-running #deciding-the-size-of-the-sliding-training-window-and-backtesting-duration
- Lookahead safety facts: "**Backtesting calls `set_freqai_targets()` one time for each backtest window** … Doing this means that the targets simulate dry/live behavior **without look ahead bias**. However, the definition of the features in `feature_engineering_*()` is performed **once on the entire training timerange**. This means that you should be sure that features do not look-ahead into the future." **Verified** — freqai-running (backtesting Note). Freqtrade also ships `lookahead-analysis` and `recursive-analysis` commands for strategies generally. **Verified** — strategy-customization (Lookahead and recursive analysis note), docs nav.
- Prediction reuse: FreqAI saves backtest predictions (`backtesting_predictions/`, feather) keyed by `identifier`; tweaking **entry/exit criteria** reuses them, but changing **features** requires a new `identifier`. `save_backtest_models: True` saves trained models; `--freqai-backtest-live-models` reuses live/dry-collected predictions. **Verified** — freqai-running #saving-backtesting-prediction-data
- **Cost modeling:** FreqAI backtesting runs through the standard freqtrade backtesting module, where fees are the config/`fee` fallback to exchange defaults — "Fee is applied twice for each trade, once when buying, once when selling" — plus the documented slippage/price-side mechanics of order pricing. There is **no FreqAI-specific cost model** in the docs. **Verified** — configuration `fee` parameter table entry; freqai-running page contains no separate fee discussion.
- Hyperopt with FreqAI: only entry/exit thresholds/criteria are hyperoptable ("It's not possible to hyperopt indicators in the `feature_engineering_*()` and `set_freqai_targets()` functions … you cannot optimize model parameters using hyperopt"); `--analyze-per-epoch` incompatible. **Verified** — freqai-running #hyperopt

### 3.5 Retrain cadence — options vs our 1h candles

- **Dry/live:** "New models are typically generated **as often as possible**, with FreqAI managing an internal queue of the coin pairs to try to keep all models equally up to date … If you do not want FreqAI to retrain new models as often as possible, you can set `live_retrain_hours` to tell FreqAI to wait at least that number of hours before training a new model." Parameter table: `live_retrain_hours`, float > 0, default 0 (= as often as possible). **Verified** — freqai-running #live-deployments + parameter table.
- **Staleness guards:** `expiration_hours` — "Avoid making predictions if a model is more than `expiration_hours` old" (default 0 = never expire; docs example 0.5 h); `expired_hours` — used to tag `do_predict == 2` (avoid predictions from models older than that). **Verified** — freqai-running #defining-model-expirations + parameter table + dataframe-key table.
- Retraining happens on a **separate thread** from inference and trading ("Threading allows for adaptive model retraining on a separate thread … Newest models and data are kept in RAM for rapid inferencing"); per-pair training is sequential in a queue; models saved to disk (`purge_old_models`, int N keeps latest N, default 2; `wait_for_training_iteration_on_reload` on shutdown). **Verified** — freqai intro features list + freqai-running #purging-old-model-data + parameter table.
- **Mapping onto 1h candles (arithmetic, from verified doc facts only):** hourly retrain cadence = `live_retrain_hours: 1.0` in dry/live; in backtesting, `backtest_period_days` = 1/24 ≈ 0.0417 for one model per hourly candle — the docs' own warning applies verbatim: fractional windows inflate training counts ("a true backtest of FreqAI adaptive training would take a very long time … The best way to fully test a model is to run it dry") — e.g. a 180-day range at 0.0417 ⇒ ≈ 4,320 trainings × pairs. These numbers follow directly from the docs' formula; the cadence *choice* is not made here.
- `continual_learning` (default False; experimental, "high probability of overfitting"; disables PCA). **Verified** — freqai-running #continual-learning.

### 3.6 Data needs (per-pair history depth)

- Live/dry: "FreqAI automatically downloads the proper amount of data needed to ensure training of a model through the defined `train_period_days` and `startup_candle_count`." **Verified** — freqai-running #automatic-data-download
- Backtesting requires manual `download-data` covering backtest start − `train_period_days` − `startup_candle_count` × timeframe: docs' worked example (30-day `train_period_days`, `startup_candle_count: 40`, max `include_timeframes` 1h → download starts 31.7 days earlier). **Verified** — freqai-running #downloading-data-to-cover-the-full-backtest-period
- FreqAI verifies exchange history sufficiency; `override_exchange_check` exists to force-skip (docs caution). **Verified** — parameter table extraneous parameters.
- Our own depth arithmetic: e.g. `train_period_days: 90` + startup 200 × 1h candles ⇒ ~90 + 8.4 days of pre-backtest history per pair (same formula as the doc example). Fact only; the choice is not made here.

### 3.7 Walk-forward mapping (FreqAI ↔ 2606.00060 protocol)

Paper (all **Verified** against https://arxiv.org/abs/2606.00060 and full-text https://arxiv.org/html/2606.00060v1):
- Data: ~70,000 hourly BTC/USDT observations 2018–2026 (Binance futures bars); target = one-step-ahead hourly log return `r_{t+1} = ln(P_{t+1}/P_t)` (eq. 1); models XGBoost / LSTM / iTransformer as **regressors**.
- Walk-forward protocol (§3.4, §4.2): "**non-anchored rolling walk-forward**", each fold = **12-month training + 3-month validation + 3-month test**, whole window **advances 3 months** per fold → **27 sequential test folds**; validation used for hyperparameter tuning, early stopping, model selection; after selection "the model is retrained on the combined training-plus-validation sample and then applied to the held-out test window"; feature construction/scaling/target-standardisation repeated **independently inside each fold** ("Temporal integrity is maintained at every stage").
- Trading: sign-based rules (long-only eq. 2, long-short eq. 3); net return eq. 4 with `c = 0.001` (10 bps per position change, all-in proxy).

FreqAI mapping — the parts that align factually:
- FreqAI's sliding window is **non-anchored/rolling**: new model trains on `train_period_days` **including** the previous window's prediction period, then predicts `backtest_period_days` (docs quote in §3.4 above) — structurally the paper's rolling fold pattern (train → predict → slide), i.e. "**walk-forward = retrain + slide**" in FreqAI terms.
- `backtest_period_days` ↔ the paper's 3-month test window; `train_period_days` ↔ the paper's 12-month training window; slide step ↔ paper 3-month advance. The numbers are user-set, not intrinsic.
- Targets-safety: FreqAI calls `set_freqai_targets()` per window (no label lookahead), while features are computed once across the whole timerange and are the user's anti-lookahead responsibility (docs Note above) — comparable to the paper's per-fold causal feature construction but **weaker**: FreqAI does not re-run feature engineering per fold.
- `data_split_parameters` (`test_size`, `shuffle` default False "to not remove the chronological order") provides an in-train-window holdout, which can serve the validation role the paper formalizes; per-fold hyperparameter optimization (paper: Optuna per fold, 50/40 trials) has **no native per-fold equivalent** in FreqAI's loop — freqtrade `hyperopt` is a separate command and FreqAI hyperopt is restricted to entry/exit thresholds (§3.4 vs paper §4.5). Stated as structural difference, not a judgment.
- The paper is single-pair; a multi-pair FreqAI deployment generalizes per-pair (§5 below).

### 3.8 How a Decide swap preserves the `enter_long`/`exit_long` contract (v0.1 spec seam)

- The strategy contract is column-based: `populate_entry_trend()` sets `enter_long` = 1 (mandatory column, `enter_tag` optional) and `populate_exit_trend()` sets `exit_long` = 1; the bot acts on the last closed candle; in backtesting "signals are generated on candle close. Trades are then initiated immediately on next candle open." **Verified** — https://www.freqtrade.io/en/stable/strategy-customization/#entry-signal-rules and #exit-signal-rules
- FreqAI returns predictions into the same dataframe under the `&…` keys "to be used in `populate_entry/exit_trend()`" (docs' words) — i.e. a Decide implementation keeps the identical seam: EMA-cross logic inside `populate_*_trend()` is exchanged for conditions on prediction columns; nothing changes outside the strategy. **Verified** — freqai-configuration #important-dataframe-key-patterns quote (§3.1 above).
- Provisions available to gate/condition signals factually: `use_exit_signal` toggle; `exit_profit_offset` ("Exit-signal is only active above this value" — with `exit_profit_only=True`); `ignore_buying_expired_candle_after` (seconds a signal stays valid); volume>0 guard in the docs' samples. **Verified** — configuration table + strategy pages. ## 4. Cost-aware execution filter (2606.00060)

- **What the paper does (exact):** "The cost-aware version allows a position change only when the forecast magnitude exceeds a threshold proportional to the transaction cost generated by the trade. The threshold is governed by a parameter λ, which controls how selective the execution rule is." Formal rule (eq. 5): update position from `pos*_t` (forecast-implied) to `pos_t` **only if** `|r̂_{t+1}| > λ · c · |pos*_t − pos_{t−1}|`; else keep the previous position. Main specification: `c = 0.001`, `λ = 2.0` ⇒ "a long-only entry or exit requires a forecast magnitude above **0.20%**, while a long-short reversal requires a forecast magnitude above **0.40%** because the turnover is two units." Costs enter returns as `r_net = pos·(e^r − 1) − c·|pos_t − pos_{t−1}|` (eq. 4); "c=0.001 … interpreted as a conservative effective cost that includes explicit exchange fees, spread crossing, slippage". Abstract (HTML version) says the filter "**permits** trades only when the forecast magnitude exceeds a transaction-cost-based threshold, sharply reduces turnover and restores profitability in selected configurations." **Verified** — https://arxiv.org/html/2606.00060v1 §4.1; note the arXiv abs-page abstract renders nearly the same sentence but with "prevents trades only when…" — wording discrepancy noted in §6; the formal equation is unambiguous.
- The paper's filter is a **position-change (turnover) filter**: it suppresses weak forecasts fluctuating around zero; robustness section 6.1 covers "Cost-aware threshold sensitivity" (existence verified from the paper's table of contents; parameter sweep values not extracted this run — **Unverified** detail).
- **Factual mapping to freqtrade hooks (no design decisions):**
  - The forecast-magnitude gate is implementable as an extra boolean condition inside `populate_entry_trend()` / `populate_exit_trend()` on returned prediction columns (`&…` values or classifier-derived scores) — the exact place docs designate for using FreqAI predictions (§3.8). **Verified** — freqtrade docs (signal columns) + FreqAI docs (prediction keys).
  - Turnover-suppression analogues that already exist as configuration/strategy facts: signal validity window `ignore_buying_expired_candle_after`; exit threshold-style gating `exit_profit_only` + `exit_profit_offset` (config table quote in §3.8); per-pair CooldownPeriod after each exit (§2.1); the protections' entry locks (§2). Each maps to *one* aspect of the paper's rule (entry gating / exit gating / post-exit pause); a per-trade λ·c-style magnitude test itself has no prebuilt knob — it is a strategy-code expression. **Verified** for each named knob (configuration/strategy pages); absence claim limited to this run's fetched pages.
  - Note for long-only spot: the paper's long-only arm is the matching position space (pos ∈ {0, 1}); the 2-unit "reversal" branch of eq. 5 has no spot-long analogue (freqtrade spot cannot hold a short leg). **Verified** (spot constraints from project harness + MISSION out-of-scope; the paper's own two branches are doc-verified).

## 7. Design implications for v0.2 (neutral list — facts only, no decisions)

- **Pairlist:** factual reproducibility constraints — VolumePairList (and PercentChange/Delist/FullTrades/Performance) are backtest-unsupported; FreqAI additionally forbids dynamic-add-remove pairlists; StaticPairList (optionally + seeded ShuffleFilter) is the documented combination compatible with backtesting and FreqAI.
- **Sizing arithmetic (facts to compute against):** fixed stake ⇒ engaged cap = `stake_amount × max_open_trades`; `tradable_balance_ratio` (default 0.99) trims tradable balance and applies to *current* (not starting) balance; `unlimited` stake ⇔ `balance / (max_open_trades − open)`; `available_capital` for multi-bot isolation; `amend_last_stake_amount` affects only the final slot under static stake.
- **Rail consequences to re-derive under N pairs:** StoplossGuard `only_per_pair: False` aggregates losing stoplosses from **all** pairs into one global trigger (`pair = "*"` lock); MaxDrawdown feeds a single global realized-DD metric from **all** pairs' closed trades; CooldownPeriod stays per-pair; a pair-scoped protection family (LowProfitPairs; StoplossGuard `only_per_pair: True`) exists in docs. `trade_limit` thresholds interact linearly with number of simultaneously-trading pairs for trigger frequency; locks affect entries only.
- **FreqAI integration surface:** `freqai.enabled` + `identifier`; features in `feature_engineering_*` (`%`), labels in `set_freqai_targets` (`&`), `self.freqai.start()` inside `populate_indicators` only; predictions return under label keys for the unchanged `enter_long`/`exit_long` seam; `startup_candle_count` sizing; `do_predict`/`DI_values` as documented prediction-trust channels.
- **Classifier adapters:** bundled classifiers = LightGBMClassifier(+MultiTarget), XGBoostClassifier, XGBoostRFClassifier, SKLearnRandomForestClassifier (sklearn RF wrap pattern), PyTorchMLPClassifier; CatBoost absent on stable; other sklearn estimators require a documented custom `IFreqaiModel` path; classifier labels are string classes in a single `&` column (multi-class e.g. up/down/same; `label_period_candles` offsets the label window).
- **Cadence knobs:** live/dry retrain = as-often-as-possible by default, throttled by `live_retrain_hours`; staleness via `expiration_hours` (prediction refusal) and `expired_hours` (do_predict==2); backtest cadence via `backtest_period_days` (fractional = sub-daily) with the docs' own training-cost warning (models = timerange ÷ backtest_period_days × pairs); per-window target recomputation is automatic, feature-engineering is once-per-timerange (lookahead responsibility on features); `lookahead-analysis`/`recursive-analysis` commands exist for verification.
- **Walk-forward discipline mapping:** FreqAI's sliding window structurally matches a non-anchored walk-forward (train `train_period_days` → predict `backtest_period_days` → slide, overlapping windows including prior predictions); the paper's **validation** stage (3-month, per-fold Optuna, train-then-retrain-on-train+val) has no native per-fold FreqAI equivalent; `data_split_parameters.test_size` with `shuffle: False` is the documented chronological holdout inside the window.
- **Cost-aware filter:** paper rule = `|r̂| > λ·c·|Δpos|` (c = 0.001, λ = 2.0 ⇒ 0.20% long-only arm); freqtrade hook surface facts = signal-column conditions in `populate_entry/exit_trend` (where FreqAI predictions land), plus existing gate knobs (`exit_profit_offset`, `ignore_buying_expired_candle_after`, per-pair CooldownPeriod, protection locks); the λ·c magnitude test itself is strategy-code, and the paper's long-short branch has no spot-long analogue.
- **Per-pair model organization:** one model per whitelist pair is the only documented mode; cross-pair context = `include_corr_pairlist` features; per-pair sequential training queue + `expiration_hours` address model-age skew; no shared-model documentation found on stable pages.
- **Data provisioning:** `train_period_days + startup_candle_count` pre-history per pair (auto in dry/live; manual `download-data` before backtesting; docs' worked example formula); history-depth guard `override_exchange_check`; live candle-limit cap `ohlcv_candle_limit × 5`.
