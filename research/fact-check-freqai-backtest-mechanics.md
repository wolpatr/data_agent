## 1. FreqAI backtesting invocation semantics — one invocation slides internally

**Verdict: CONFIRMED.** One `freqtrade backtesting --timerange T1-T2 --freqaimodel X` invocation runs the full walk-forward internally: FreqAI derives training timeranges from `train_period_days`, slides both windows by `backtest_period_days`, retrains the model at every slide, and makes predictions only on the backtest (future) portion of each window. The whole user `--timerange` is the **backtest/evaluation window; it does NOT include the training span — training data is automatically prepended before T1**.

Source mechanics (installed 2026.10):

- `freqai/freqai/data_kitchen.py:86-97` — on each pair's backtest entry, `FreqaiDataKitchen.__init__` (non-live) builds:
  - `self.full_timerange = self.create_fulltimerange(self.config["timerange"], self.freqai_config.get("train_period_days", 0))` — **note the second argument: the full timerange start is shifted back by `train_period_days`, not `backtest_period_days`** (function signature names the param `backtest_period_days` but the caller passes `train_period_days`: `data_kitchen.py:479-505`, extension at `:502-504`).
  - `(self.training_timeranges, self.backtesting_timeranges) = self.split_timerange(self.full_timerange, train_period_days, backtest_period_days)` (`:93-97`).
- `data_kitchen.py:316-372` — `split_timerange()`: starting at `full_timerange.startts` (= T1 − train_period_days), loop:
  - `timerange_train.stopts = timerange_train.startts + train_period_days` → **first train window is exactly [T1 − 365 d, T1)** for `train_period_days: 365`;
  - `tr_backtest = [train_stop, train_stop + bt_period]`, clipped to `config_timerange.stopts` (`:361`) → for `backtest_period_days: 7`, backtest windows are `[T1, T1+7d)`, `[T1+7d, T1+14d)`, … , last one clipped to T2;
  - slide step: `timerange_train.startts += bt_period` (`:350`);
  - loop breaks when `timerange_backtest.stopts == config_timerange.stopts` (`:368`).
  - Note `create_fulltimerange` raises on open-ended ranges ("FreqAI backtesting does not allow open ended timeranges", `:493-497`) — T2 must be explicit.
- `freqai/freqai/freqai_interface.py:272-409` — `start_backtesting()`: `for tr_train, tr_backtest in zip(dk.training_timeranges, dk.backtesting_timeranges)` (`:300-302`); per slide it trains a fresh model (`self.train(dataframe_train, pair, dk)` `:373`), names it by `timestamp_model_id = int(tr_train.stopts)` (`:320`), then `self.predict(dataframe_backtest, dk)` (`:401`). Docstring (`:276-281`): "FreqAI slides the window and sequentially builds the backtesting results before returning the concatenated results for the full backtesting period back to the strategy." Prediction reuse: `dk.check_if_backtest_prediction_is_valid(...)` (`:328`) + `backtesting_predictions/` feather files allow re-running entry/exit criteria with the same `identifier` without retraining (docs: freqai-running "Model reuse").
- Train data provenance: the strategy dataframe passed to FreqAI contains "entire backtesting timerange + additional historical data necessary to train the model" (`freqai_interface.py:135-137`); train slices cut from `dataframe.loc[dataframe["date"] < tr_train.stopdt]` (`:347-359`). Trade simulation still covers exactly T1–T2: `backtesting.py:545-548` trims the analyzed dataframe to `--timerange` (minus startup candles) before signal simulation, and pre-window prediction rows are zero-filled (`data_kitchen.py:465-477`, `fill_predictions`).
- **startup/train data before the timerange: automatic.** With `freqai.enabled`, `required_startup` becomes `startup_candle_count + train_period_days·86400/tf_seconds` candles (`data/dataprovider.py:338-353`, "Increasing startup_candle_count for freqai …"); `load_bt_data` loads with `startup_candles=self.required_startup` (`optimize/backtesting.py:364-373`). If not enough history exists, `timerange.adjust_start_if_necessary` silently shifts the backtest start FORWARD (`backtesting.py:383-386`) instead of failing — **the runner must pre-check data coverage** (docs recommend downloading ≥ `train_period_days + startup_candle_count` earlier than T1; freqai-running "Downloading data to cover the full backtest period").
- `--freqai-backtest-live-models` is an alternative path that replays historic live predictions (`freqai_interface.py:159-165`, `backtesting.py:217-220`); not relevant to the runner's default path.

Docs cross-checks:
- https://www.freqtrade.io/en/stable/freqai-running/ — "Deciding the size of the sliding training window and backtesting duration": "The 'sliding window' then moves one week forward … the new model uses the previous 30 days … This is repeated until the end of `--timerange`" and the `20210501-20210701` + 7-day windows "8 separate models" example. Same page: data-download must reach back `train_period_days + startup_candle_count` before the backtest start.
- https://www.freqtrade.io/en/stable/freqai-parameter-table/ — `train_period_days`, `backtest_period_days` ("Number of days to inference … before sliding the window and retraining … the provided `timerange` will be divided by this number to yield the number of trainings").

Runner implication: one invocation = one trial covering T1–T2 with folds of `backtest_period_days`; set `backtest_period_days` to the desired fold cadence (e.g. a quarter as one fold = 92, or keep 7 and re-aggregate). **Caveat:** the `backtest cache` (section 5) and FreqAI prediction caching (same `identifier` + same config) mean an identical rerun may reuse stored models/predictions — change `identifier` per trial.

## 2. Per-window metrics extraction — artifacts per invocation

**What one invocation writes** (to `user_data/backtest_results/` by default, controllable via `--backtest-directory`/`--export-directory`):

- Export happens only with `--export` in `{"trades","signals"}` (choices `constants.EXPORT_OPTIONS = ["none","trades","signals"]`, help says default `trades`) (`optimize/backtesting.py:1950`; `commands/cli_options.py:240-244`). File naming: `backtest-result-<YYYY-MM-DD_HH-MM-SS>.zip` + sibling `backtest-result-<appendix>.json` (metadata) + `.last_result.json` pointer (`optimize/optimize_reports/bt_storage.py:33-83`; `constants.LAST_BT_RESULT_FN = ".last_result.json"`). `--backtest-filename` is deprecated for backtesting per CLI help.
- Zip contents (`bt_storage.py:86-167`, docs "Backtest output file"):
  - `backtest-result-<appendix>.json` — the full stats: `strategy` and `strategy_comparison`; per strategy this includes the **complete per-trade list** (`"trades"` — each with open/close timestamps, profit, pair, tags …), `periodic_breakdown` (`optimize/optimize_reports/optimize_reports.py:628-630`, `:735`), summary metrics (sharpe/sortino/calmar/sqn/p_value/expectancy, wallet stats — `:655-738`), and result metadata (`freqaimodel`, `freqai_identifier`, `timerange`, `max_open_trades`, balances — `:714-734`).
  - `backtest-result-<appendix>_config.json` — **sanitized snapshot of the full config** (`sanitize_config(config["original_config"])`, `bt_storage.py:96-98`).
  - a **copy of the strategy .py file** used (`:100-110`) and its serialized params (`:111-134`);
  - `<stem>_market_change.feather` (per-candle market close change, `:137-144`), wallet feather summaries, and — only with `--export signals` — `signals/rejected/exited` pickles (`:155-167`, condition `config["export"] == "signals"`).
  - Per-strategy metadata JSON next to the zip (`backtest-result-<appendix>.meta.json`, `backtest_caching.py:41-44`, written at `bt_storage.py:79`) with per strategy: `run_id`, `backtest_start_time`, `timeframe`, `timeframe_detail`, `backtest_start_ts`, `backtest_end_ts`, optional `notes` (`optimize_reports.py:806-826`).
- `--breakdown {day,week,month,year,weekday}` (`commands/cli_options.py:279-283`; choices `constants.BACKTEST_BREAKDOWNS = ["day","week","month","year","weekday"]`): **display-only tables from already-exported trades** (`optimize/optimize_reports/bt_output.py:560-618`). The underlying stats are computed for ALL five periods regardless of the flag and land in the export (`optimize_reports.py:628-630`,`:413-417`) — bucketed by trade **close_date** (`:383-408`).
- `freqtrade backtesting-show` re-displays a stored result from `user_data/backtest_results` without rerunning (`args` `backtest_show_*` in `commands/arguments.py:99-106`; `bt_output.py` `show_backtest_results`); `freqtrade backtesting-analysis` (`arguments.py:529-534`, `commands/analyze_commands.py`) replays **signal-level** analysis from the pickles written under `--export signals` (`data/entryexitanalysis.py:344-405`) — it needs a fresh export with `signals`, it is not a per-fold metric tool.

**Per-sub-window aggregates without rerunning: YES for trade-based metrics.** The exported `trades` list lets the runner recompute any window (e.g. 3-month test folds: filter trades by close/open date, recompute win-rate, per-fold profit, profit factor, expectancy) without reruns; the built-in `periodic_breakdown` gives month/week already. Two honest limits: (a) wallet-path metrics (drawdown sequences, final balance) depend on trade sequencing/compounding across window boundaries — fold-local recomputation from the trades sequence is approximate relative to a genuine isolated run (balances roll over); (b) `--breakdown month` buckets by month-end date, not by your fold boundaries — fold boundaries need custom aggregation from `trades`. So: rerunning per 3m test window is NOT required for headline trade metrics, but IS the clean path when you want fold-isolated wallet/path-independent simulation semantics (fresh wallet per fold) that a single invocation's compounding does not provide.

## 3. k-fold/seed levers inside FreqAI training

**Verdict: no native k-fold; only the sklearn `train_test_split` passthrough.** 

- `freqai_info["data_split_parameters"]` is forwarded **verbatim as `**kwargs` to sklearn's `train_test_split`**: `freqai/freqai/data_kitchen.py:145-158` — if `test_size != 0` (default `0.1`), `train_test_split(filtered_dataframe, labels, weights, **self.config["freqai"]["data_split_parameters"])`. So `shuffle`, `test_size`, and `random_state` pass straight through; **`shuffle` defaults to `False` if you don't set it** (`:136-137` — "shuffle" is injected with `False` when absent).
  - `stratify` is impractical via config: it needs an array the same length as the fit-time dataset; the config dict is static (verified: no `stratify` anywhere in the installed package).
  - `random_state` is accepted (plain passthrough) → **repeated train/test splits with different seeds ARE expressible**: run N trials with `data_split_parameters.random_state = s_i` (each invocation = one trial). Deterministic given the same dataset size.
- `data_kitchen.py:167-187` — `shuffle_after_split` (a `feature_parameters` flag, not data_split_parameters) shuffles via `random.randint(0,100)` on Python's **global** RNG (`rint1`/`rint2`) — **not config-seedable**; avoid for reproducible trials unless seeding the global RNG externally (not supported by freqtrade).
- The split's `test` set is used as LightGBM `eval_set`/early-stopping-ish evaluation input, not as selection logic: `freqai/prediction_models/LightGBMClassifier.py:33-63` — `model = LGBMClassifier(**self.model_training_parameters)`; `model.fit(X, y, eval_set=eval_set, sample_weight=train_weights, eval_sample_weight=[test_weights], ...)` (fit path: base class `train()` in `freqai/base_models/BaseClassifierModel.py:24-85` → `self.fit(dd, dk)`, i.e. `model.fit(..., dk.data_dictionary)` per `IFreqaiModel.fit` contract `freqai_interface.py:989-997`). `model_training_parameters` is a raw passthrough to `LGBMClassifier(**kwargs)` — **`random_state` there seeds LightGBM itself** and is the practical determinism lever.
- **k-fold (k=5) cannot be expressed natively**: grep for `KFold|StratifiedKFold|cross_val|kfold` over `freqtrade/freqai` and `freqtrade/data` returns **zero matches**. Options: (a) opt-in k-fold = N separate invocations with different `data_split_parameters.random_state` (repeated holdout, not true k-fold, and the freqtrade trade-level metrics always come from the SAME walk-forward predictions); (b) subclass `LightGBMClassifier.train()`/`fit()` to run `sklearn.model_selection.KFold` inside the 12m train window yourself (the docs' recommended extension point: "override the common `fit()`, `train()`, or `predict()`").
- No documented FreqAI config "seed": the parameter table documents only `test_size` and `shuffle` under `data_split_parameters` (https://www.freqtrade.io/en/stable/freqai-parameter-table/ — "Data split parameters"); `freqai-running` says `data_split_parameters` "can be any parameters associated with scikit-learn's `train_test_split()` function". No global random-seed config exists for freqtrade backtesting (only hyperopt has `hyperopt_random_state`).

Docs cross-checks:
- https://www.freqtrade.io/en/stable/freqai-running/ — "Controlling the model learning process": `model_training_parameters` = any library params; `data_split_parameters` = any `train_test_split()` params (incl. `shuffle`).
- https://www.freqtrade.io/en/stable/freqai-parameter-table/ — `shuffle` default `False`, `test_size`, plus `shuffle_after_split`/`reverse_train_test_order` under `feature_parameters`.

## 4. Strategy retirement mechanics — recursive scan?

**Verdict: by-name resolution is TOP-LEVEL ONLY (non-recursive) by default; recursion is opt-in.**

- `freqtrade/resolvers/iresolver.py:131-160` — `_search_object()` iterates `sorted(directory.iterdir())`, requires `entry.suffix == ".py"`, never recurses into directories. This is the path used for `--strategy Name` resolution (`resolvers/strategy_resolver.py:297-302`).
- `resolvers/strategy_resolver.py:256-310` — `_load_strategy()`: search paths = (optional `--strategy-path`, then `user_data/strategies`); **only when config `recursive_strategy_search: true`** does it add sub-directories via `os.walk` (`:267-272`). CLI flag `--recursive-strategy-search` (`commands/cli_options.py:110-115`; part of `ARGS_STRATEGY`, `commands/arguments.py:27-33`) sets the same config key.
- `freqtrade list-strategies` uses `StrategyResolver.search_all_objects(config, enum_failed, config.get("recursive_strategy_search", False))` (`commands/list_commands.py:159-161`); recursion in `_search_all_objects` descends only into dirs not starting with `__`/`.` (`iresolver.py:268-277`).
- **Plug-out consequence:** moving a retired strategy to `user_data/strategies/retired/foo.py` makes it unresolvable for both `backtesting --strategy Foo` and default `list-strategies` — clean plug-out. Two caveats: (1) if anyone sets `recursive_strategy_search: true`, the retired file becomes loadable/listable again ("retired" is then purely organizational); (2) `_get_valid_object` still imports any top-level `.py` when listing — keep malformed/experimental code out of the top level to avoid load noise.
- Docs: https://www.freqtrade.io/en/stable/backtesting/ (command reference shows `--recursive-strategy-search` — "Recursively search for a strategy in the strategies folder").

## 5. Deterministic hashing inputs — what to hash for a run record

**What freqtrade itself produces and uses for identity:**

- **`run_id`** (`optimize/backtest_caching.py:8-38`, `get_strategy_run_id`): SHA1 over (a) the full config JSON **minus `strategy_list, original_config, telegram, api_server`** (serialized with `rapidjson`, NaN-permissive), (b) `strategy.ft_used_params` (params file/API overrides), (c) **the raw bytes of the strategy `.py` file**. Docstring: "Identical config and strategy file will always return an identical hash." It is stored per-strategy in result `metadata` (`optimize_reports.py:813`), and per-strategy stats expose `"run_id"` (`backtesting.py:1865`).
  - This hash **includes the FreqAI identifier** (any config value it is) but **not the FreqAI model class file** (`--freqaimodel` name string only), not the freqtrade version, and not the data files — so the runner must add those to its own run record.
- **Backtest cache** uses the same identity: `--cache {none,day,week,month}` (default `day`) reuses an existing result when config+strategy match (`backtesting.py:1885-1908`, `1926-1931`; docs "Backtest result caching" — "reuse a cached result from within the last day when the backtested strategy and config match that of a previous backtest. To force a new backtest … specify `--cache none`"). **For the ML runner: either pass `--cache none` or guarantee the config differs per trial (e.g. unique `freqai.identifier`), otherwise identical-config invocations may return the cached result.**
- **Exported snapshot** (zip, section 2): sanitized full config JSON + the strategy .py + strategy params — i.e., the export itself carries the primary reproducibility inputs; docs note only those two are included, "eventual dependencies are not included".
- **FreqAI-side record:** `record_params()` (`freqai/freqai/utils.py:156-178`, invoked in `IFreqaiModel.__init__` `freqai_interface.py:118`) writes `user_data/models/<identifier>/run_params.json` containing the whole `freqai` sub-config + timeframe/stake/pairs. Per-train-window artifacts land under `user_data/models/<identifier>/sub-train-<COIN>_<trainstop-ts>/` (feature list, pipelines, model, tensorboard logs; predictions under `.../backtesting_predictions/`).

**Recommended run-record hash inputs** (to make each persisted trial reproducible/identifiable):
1. Config file contents (the export already snapshots a sanitized copy — keep that, but hash the true input file(s) you passed; `run_id` covers this modulo the four excluded keys listed above).
2. Strategy file bytes (already inside `run_id` and the zip).
3. FreqAI model class identity: `--freqaimodel` name **plus** the hash of the prediction-model file for custom classes (freqtrade does not hash this; for `LightGBMClassifier` the installed version pin suffices).
4. Installed package versions: `freqtrade==2026.10`, `lightgbm` version, numpy/pandas — the runner's own pin, out of freqtrade's control.
5. Data identity: freqtrade does **not** hash candle data; records should store the downloaded timerange, pairlist, timeframe(s), and `freqtrade download-data` invocation or a data-file checksum.
6. DB: not applicable to backtesting exports (SQLite is live/dry state; trades list lives in the export). The `metadata` JSON fields (`run_id`, `backtest_start_ts/end_ts`, `timeframe`, `notes`) are the built-in per-run identifiers (`optimize_reports.py:806-826`).
- There is no field literally named `config_hash` in the installed package; the equivalent is `metadata[].run_id` + the `_config.json` snapshot inside the zip.

## Spec inputs

- Backtest engine/kernel: freqtrade **2026.10** (installed package verified; `freqtrade.__version__ == "2026.10"`).
- One invocation of `freqtrade backtesting --timerange T1-T2 --freqaimodel LightGBMClassifier` runs the whole walk-forward internally: FreqAI prepends `train_period_days` of data before T1 automatically, trains fresh per slide of `backtest_period_days`, predicts only on slides, trades simulated only within T1–T2.
- Runner invocation template: `freqtrade backtesting … --timerange <T1>-<T2> --freqaimodel LightGBMClassifier --export trades --cache none [--breakdown month]`; T2 must be an explicit close-ended timestamp (open-ended FreqAI timeranges raise); ensure downloaded data covers `T1 - train_period_days - startup_candle_count` (else the backtest start silently shifts forward).
- Fold cadence = `freqai.backtest_period_days` (integer; e.g. 7 for weekly retrain sliding, or coarser for quarterly headline folds per arXiv 2606.00060 windows); each trial gets a unique `freqai.identifier` to avoid FreqAI prediction/model reuse.
- Artifacts per trial (single invocation): `user_data/backtest_results/backtest-result-<ts>.zip` (trades list + `periodic_breakdown` day/week/month/year/weekday + summary metrics + sanitized config + strategy.py + market_change.feather; signals/rejected/exited pickles only under `--export signals`) + sibling `*.meta.json` (`run_id`, timestamps) + `.last_result.json` pointer + `user_data/models/<identifier>/` model/prediction artifacts incl. `run_params.json`.
- Per-fold metrics policy: recompute trade-based fold metrics from the exported `trades` list (no rerun needed); rerun-per-test-window only when fold-isolated wallet semantics (fresh balance per fold) are required; `--breakdown` is display-only and its stats are bucketed by calendar periods, not fold boundaries.
- k-fold (opt-in, k=5): NOT native; repeat trials with distinct `data_split_parameters.random_state` (sklearn `train_test_split` passthrough; `shuffle` defaults False; `stratify` unusable via config) or subclass `LightGBMClassifier.fit()` to run `KFold` inside each 12m train window; seed LightGBM itself via `model_training_parameters.random_state`.
- Retired strategies: move to `user_data/strategies/retired/` — resolver scans only top-level `.py` unless `recursive_strategy_search: true`/`--recursive-strategy-search` is set (then it becomes loadable again).
- Reproducibility: hash per trial = true config file contents + strategy file bytes + freqaimodel class identity + package versions (freqtrade/lightgbm) + data range/pairlist/timeframe checksum; freqtrade's own identity is `metadata[].run_id` (SHA1 of de-telegramized config + used params + strategy bytes, includes `freqai.identifier`) plus the sanitized config snapshot inside the export zip; always `--cache none` (or unique identifier) to avoid `--cache`/prediction reuse; freqtrade does not hash candle data.
